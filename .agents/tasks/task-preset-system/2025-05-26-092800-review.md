# Preset system for Vira Sections Elementor widgets

A centralized preset system lets editors one-click-fill widget settings from page-specific content profiles. A static PHP class (`Vira_Sections_Presets`) holds all text, colors, and repeater data for 12 widgets across 4 page designs. A trait injects a dropdown at the top of each widget's Content tab, and a small JS file in the editor applies the preset values to the Backbone model when the user picks one.

**Watch for:** The JS handler accumulates event listeners on every panel open without cleanup (confirmed). The entire preset payload (~60KB+ of JSON) is localized into every editor page load regardless of which widgets are on the page (confirmed). The `get_preset_defaults()` trait method is defined but never called anywhere (confirmed) — the server-side application path is dead code.

## High-level view

The architecture splits cleanly: PHP owns the data and the Elementor control registration, JS owns the runtime application of presets in the editor. The data class is purely static with no database access, which keeps the implementation simple but means any content update requires a code deploy.

The JS preset handler has two structural problems: it adds a `change` event listener to `panel.el` on every `panel/open_editor/widget` hook invocation without ever removing it, creating a listener leak that compounds as users click between widgets; and it relies on `model.renderRemoteServer()` to refresh the panel, which triggers a server-side render round-trip rather than simply refreshing the panel controls in place.

The full preset dataset for all 12 widgets is serialized via `wp_localize_script` into a single `ViraPresetsData` global on every editor load. For a plugin with ~676 lines of PHP array data (much of it Persian text with repeater structures), this means a non-trivial JSON blob inlined into the page HTML on every Elementor editor session.

## Event listener accumulation in preset-handler.js

Every time Elementor opens the editor panel for any Vira widget, the `panel/open_editor/widget` hook fires and `bindPresetHandler` attaches a new `change` listener to `panel.el`. The listener is never removed. If a user clicks between 10 widgets (even the same one reopened), 10 duplicate listeners exist. Each fires `applyPreset`, which is idempotent per invocation but wastes cycles and — if the preset involves expensive model operations — multiplies them.

The fix is straightforward: either mark `panel.el` with a data attribute after binding and skip if present, or use a named function with `removeEventListener` before `addEventListener`.

Additionally, the 500ms `setTimeout` fallback for when the control DOM isn't ready is fragile. If the panel renders in 600ms, the handler binds but the control still isn't present; if it renders in 200ms, the timeout was unnecessary overhead. Elementor provides `panel/open_editor/widget` as the reliable hook precisely because the panel is ready — the missing control is more likely a symptom of the section being collapsed or the control being inside a tab that hasn't rendered. A MutationObserver on the panel root would be more robust than a fixed timer.

## Dead code: `get_preset_defaults()`

The trait's `get_preset_defaults()` method retrieves the current widget settings, checks the `vira_preset` value, and returns the corresponding preset array. This could be used server-side in `get_settings_for_display()` to merge preset values into rendering — effectively making the preset apply even without JS. But no widget calls it, and the render methods don't reference it.

This creates a confusing contract: a developer reading the trait sees two methods and assumes both are needed. Either document it as "reserved for future SSR preset application" or remove it.

## Payload size and localization strategy

`get_all_presets_for_js()` iterates all 12 widget entries in `$widget_pages` and calls `get_presets()` for each, collecting the full dataset. This is then passed to `wp_localize_script`, which JSON-encodes it into an inline `<script>` tag. The `class-presets.php` file is 676 lines of dense PHP arrays; the JSON equivalent will be larger due to key repetition and lack of PHP's `array_merge` compression.

For a small internal plugin this is acceptable, but the pattern doesn't scale. If more pages or widgets are added, the payload grows linearly. A lighter approach would localize only the widget names that exist on the current page (query `\Elementor\Plugin::$instance->documents->get_current()` for active widget types) or fetch presets via AJAX on dropdown open.

## `renderRemoteServer()` side effects

After applying preset values to the Backbone settings model, the JS calls `model.renderRemoteServer()`. This triggers Elementor's server-side widget render — an AJAX POST to `wp-admin/admin-ajax.php` with the full widget settings, which returns rendered HTML for the preview. The panel controls won't visually update to reflect the new values until the user manually switches tabs or clicks away, because `renderRemoteServer` refreshes the *preview iframe*, not the *panel inputs*.

To update both preview and panel, the code should trigger the settings model's change events properly (so Elementor's reactive binding updates the panel inputs) and let the preview update naturally via Elementor's live editing system.

## No revert mechanism

When the user selects "custom" (the default), `applyPreset` returns early without action. This means there's no way to undo a preset application — the dropdown is effectively a one-way operation. Once a user picks "seo-google" and all fields are overwritten, switching back to "custom" leaves the seo-google values in place. The user must either Ctrl+Z through each change or manually edit every field.

A clean solution would be to snapshot the current settings before applying a preset and restore them when "custom" is re-selected. Alternatively, the description text on the control could explicitly warn that applying a preset overwrites current values permanently.
